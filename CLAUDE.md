# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flicker is a Unity top-down 2D roguelike shooter in the style of Hotline Miami. It uses Unity **6000.6.10f1** with URP (2D renderer). Gameplay code is in `Assets/Scripts/` and compiles into the default `Assembly-CSharp`. The one exception is `Assets/Scripts/Generation/`, the pure level generator. It has its own asmdef, `Flicker.Generation`, auto-referenced so `Assembly-CSharp` sees it. It must not depend on gameplay code and must never use `UnityEngine.Random`. Its EditMode tests are in `Assets/Tests/EditMode/` (asmdef `Flicker.Generation.Tests`).

## Building / running

No CLI build scripts exist. Work happens in the Unity Editor. The project has the `com.unity.pipeline` package, so the Unity CLI (`unity`, installed at `%LOCALAPPDATA%\Unity\bin`) can drive an open Editor: `unity command script eval --file <script.cs>`, `unity command editor.playmode start|stop`, and `unity command console get`. Use it for prefab and scene edits instead of hand-editing YAML. To check that the code compiles without opening the editor, run a batchmode compile. Close the Editor first, because a project can only be opened by one Editor at a time:

```
"/c/Program Files/Unity/Hub/Editor/6000.6.10f1/Editor/Unity.exe" -batchmode -nographics -quit -projectPath . -logFile -
```

**Tests:** with the Editor open, run `unity command test run --mode editor --filter-type Assembly --filter Flicker.Generation.Tests`. If the CLI reports the Pipeline server as unreachable, the Editor is recompiling, so retry a few seconds later. New files appear only after an asset refresh (`unity command script eval --code "UnityEditor.AssetDatabase.Refresh();"`).

`Flicker.sln` / `Assembly-CSharp.csproj` are generated by Unity for IDE use. Don't edit them by hand.

**Scenes:** `MainMenu.unity` (weapon selection and start) leads to `Block.unity`, the procedurally generated level where a run is played. `Arena1.unity` is the hand-built sandbox; the menu no longer reaches it, so play it from the Editor. Scene names and tags used from code live in `Scripts/Core/SceneNames.cs` and `GameTags.cs`, so add new ones there. A new scene must also be added to `ProjectSettings/EditorBuildSettings.asset` before `SceneManager.LoadScene` can reach it.

**Render pipeline:** the active URP assets (`URP.asset`, `URP_Renderer.asset`, global settings, volume profile) are in `Assets/Settings/`.

## Architecture

**Weapons (`Scripts/Battle/Weapons`)**: Each weapon is one self-describing prefab in `Assets/Resources/Weapons/`. Nothing else lists weapons; there is no enum or index-matched array. `WeaponCatalog.All` loads every `Weapon` prefab from that folder, ordered by `sortOrder`. The menu, the player and the ammo HUD all build themselves from it.
- The abstract `Weapon` holds identity and presentation (`weaponName`, `sortOrder`, `menuIcon`, `playerSprite`, `ammoBarPrefab`), stats, fire rate/ammo/reload, and shared firing. `Shoot()` calls the abstract `PerformShot()`, which subclasses implement by calling `SpawnProjectile(rotation)` once or more. `SpawnProjectile` applies `projectileSpeed`, `projectileLifetime`, and `damagePerShot` (into `Projectile.damage`).
- `Pistol` fires one projectile, `Shotgun` fires `pellets` with random spread, and `RPG` spawns a rocket and calls `RocketProjectile.Initialize` for radius damage with falloff.
- Each weapon prefab's root position is its held offset from the player. `firePoint` is the prefab root.
- **Adding a weapon:** make a prefab (or a prefab variant, for stat-only changes) with a `Weapon` subclass, fill in its fields, and save it in `Assets/Resources/Weapons/`. Write a new subclass only for new firing behavior. No other code or scene changes are needed.

**Loadout flow:** In MainMenu, `WeaponSelectionManager` spawns one `WeaponButton` (`Prefabs/UI/Weapon Button.prefab`) per catalog weapon under a `HorizontalLayoutGroup`. On confirm it calls `WeaponSelectionData.SetSelection` (prefab references, `LoadoutSize` = 2). and loads Block. In the game scene (Block or Arena1), `WeaponManager.Awake` instantiates the selected prefabs as inactive children of the player. If nothing was selected, for example when a scene is played directly, it uses the first two catalog weapons. `AmmoUI.Start` builds one bar per `WeaponManager.EquippedWeapons` entry from its `ammoBarPrefab`. It relies on `WeaponManager` having spawned the weapons in `Awake`.

**Projectiles (`Scripts/Battle/Projectile`, `Rpg/RocketProjectile`)**: Projectiles are trigger-based (`OnTriggerEnter2D`) and filter by `LayerMask`s for the Zombie and Wall layers. The firing weapon sets their damage and lifetime, not the projectile prefab.
- Projectiles are pooled. `SpawnProjectile` gets them from `ObjectPools.Get(prefab, pos, rot)` (`Scripts/Battle/Pooling`), which keeps one `UnityEngine.Pool.ObjectPool` per prefab and is cleared on scene unload. Every pooled instance carries a `PooledObject`.
  - Never `Destroy` a projectile. Use `PooledObject.Despawn(gameObject)`, `Release()` or `ReleaseAfter(seconds)`.
  - Per-shot state must reset in `OnEnable`, not `Start`: `RocketProjectile.exploded`, `ProjectileDirection`'s initial facing, and trails (`PooledObject` clears them).
  - Effects (blood, explosion) are not pooled.
- `SpawnProjectile(rotation, autoDestroy: false)` leaves the lifetime to the projectile.
- `RPG` uses this: `RocketProjectile` explodes once, on a zombie or wall hit or when its lifetime ends (`Invoke`). All of its damage comes from the explosion. Falloff is measured to each collider's closest point, so a direct hit deals full damage.
- The effect is `Prefabs/Other/Explosion.prefab`, an unlit particle burst so it shows in darkness.

`Assembly-CSharp` and `Flicker.Generation` both ship in player builds. Never add `using UnityEditor...` to scripts under `Assets/Scripts/`.

**Enemies (`Scripts/EnemyScripts`)**: Each zombie is made of independent components. Each concern has exactly one owner:
- `ZombieAI` moves the zombie. The `NavMeshAgent` only plans: `updatePosition`, `updateRotation` and `updateUpAxis` are all false. The zombie's dynamic `Rigidbody2D` moves at `agent.desiredVelocity` in `FixedUpdate`, and `agent.nextPosition` is synced back from the body. Walls, the player and other zombies therefore collide through physics.
  - It repaths every 0.2 s.
  - It stops once the player is in reach.
  - It faces its movement direction, and turns toward the player only when close and in line of sight.
  - Its speed comes from `ZombieAI.moveSpeed`, which overrides the agent's value.
- `ZombieAttack` handles attacks. The player is in reach when the centers are within `attackRange` or the colliders touch (`contactTolerance`). Physics keeps bodies apart, so center distance alone could never reach short ranges. Attacks also require a clear `Linecast` against the Wall layer (`CanSeePlayer`).
- `ZombieHealth` is the damage receiver.
  - It owns the hit tint, changing RGB only.
  - It guards against dying twice with `IsDead`.
- `ZombieVisibility` owns alpha and changes nothing else. Every 0.05 s it asks `VisibilityLight.IsLit` (some light covers the point with no `wallLayer` linecast between them) and fades in or out. This is the core "flicker" mechanic, and fuel canisters use the same rule.

Never write a zombie's full `SpriteRenderer.color` from two scripts. Change only the channel the script owns.

The 2D NavMesh comes from **NavMeshPlus** (`com.h8man.2d.navmeshplus`), a git package pinned to a commit in `Packages/manifest.json`. Older commits fail to compile on Unity 6000.6 (`GetInstanceID` is obsolete-as-error), so only move the pin forward. NavMesh assets are baked per scene, in `Scenes/Arena1/`.
- **Agent types:** paths must be planned for the zombie's real body size, or wide zombies snag on corners. There are two agent types:
  - **Humanoid** (id 0, radius 0.4) for Zombie and Small Zombie.
  - **Large Zombie** (id 1279349319, radius 0.85) for Zombie Tank, whose ×2 box is 1.64 wide across its path.
- Every scene has one `NavMeshSurface` per agent type (`NavMesh` and `NavMesh Large`). Arena1's are editor-baked assets. `Block.unity` rebakes both at runtime through `BlockBuilder.navMeshSurfaces`.
- Tanks don't fit 2-wide doors, gates or narrow alleys. That's intended: houses and tight alleys are safe from tanks. Spawn a zombie only where `NavMesh.SamplePosition` with its own agent type succeeds, as `BlockBuilder.TryFindSpawn` does.
- A new zombie size needs a matching agent type and surface.

**Level generation (`Scripts/Generation`, `Scripts/Level`)**: one level is one city block, built from a seed.
- Pipeline (`BlockGenerator.Generate(seed, BlockGenSettings)`), all pure C#:
  1. Roll the block size.
  2. `BlockFrame`: road, barrier row, sidewalk with the car spot, and a tall-building perimeter. Under the car spot it cuts a 4-wide gap in the barrier and records `ExitCar` (4×2: barrier row + top road row). Those cells are `Road`; the exit car itself plugs the gap.
  3. `LotSplitter`: BSP into lots. Some cuts become 2–3 wide alleys that always connect back to the sidewalk.
  4. `LotTypeAssigner`: weighted choice. Parks never touch, and there is a minimum number of houses.
  5. Each lot's `ILotFiller`:
     - houses with BSP rooms and 2-wide door gaps;
     - tall-building clusters: a 2-wide alley along each closed side, then a BSP split into `tallBuildingMinSide`–`MaxSide` buildings with alleys between them;
     - parking lots and parks.
  6. `LayoutValidator`: flood fill from the car spot, plus a 2×2 check so there are no 1-wide gaps. It records `DistanceFromCar` and `SpawnHints`.
  7. `CanisterPlacer`: `canisterCount` fuel canisters from the spawn hints, never on the sidewalk, at least `canisterMinCarDistance` walking cells from the car and `canisterMinSpacing` from each other. No room fails the attempt.

  A rejected attempt retries with `Rng.Derive(seed, attempt)`, so a seed always gives the same block.
- Randomness only comes from the `Rng` passed in (mulberry32). Never use `UnityEngine.Random` or iterate unordered collections in generation code.
- **Adding a lot type:** add a `LotType` value, one `ILotFiller` class (found by reflection), and a weight in `BlockGenSettings`. Props are placed through `PropPlacer.TryPlace`, which refuses any prop that would disconnect the lot or create a 1-wide gap.
- `BlockBuilder` (in `Block.unity`) builds the layout into the scene:
  - Ground goes on the Tilemap. Its tiles use collider type Sprite, and the Tilemap object carries its own walkable `NavMeshModifier`, which NavMeshPlus needs before it will collect tiles at all.
  - Blocking cells are merged into rectangles (`GreedyRects`) and spawned as scaled `Prefabs/Level` blocks. Props go at their footprint center.
  - It spawns `Props/Exit Car.prefab` in the barrier gap (exposed as `ExitCar`) and `Props/Fuel Canister.prefab` on every canister cell.
  - Then it calls `BuildNavMesh()` on every surface in `navMeshSurfaces` at runtime and moves the player to the car spot (`PlayerSpawn`). `Generate(seed, revivePlayer)` revives them only when asked: the next level of a run keeps health.
  - Regenerating destroys the `Generated` child and waits a frame before baking.
- Tune the block in `Assets/Settings/Block Gen Settings.asset`. The builder's context menu "Generate (random seed)" previews a block in the Editor, and gizmos show lots, rooms and doors.
- `debugZombieCount` (0 by default) scatters test zombies far from the car until real spawning exists.

**Level loop (`Scripts/Level/LevelRun.cs`, on "Level Run" in `Block.unity`)**: `LevelRun` owns the run: `Level`, `Fuel`/`FuelNeeded`, `RunSeed` and `Busy` (cutscene playing).
- `FuelCanister` (trigger) raises the static `PickedUp` and destroys itself. Canisters register in `FuelCanister.All` and start hidden (alpha 0). The first time `VisibilityLight.IsLit` sees one, it becomes `Found` for good and glows: it swaps to `Sprite-Unlit-Default`, enables its pulsing `Halo` Light2D child and plays its `Sparkle` burst once.
- **Backup:** `LevelRun.LevelTime` counts only while the player has control (not `Busy`, not dead) and resets per block. At `backupDelay` (90 s) it sets `BackupActive` and calls `MakeBeacon()` on unfound canisters (glow without counting as found; one-way). While the player rides the car, `FuelCanister.RevealPaused` stops the headlights from finding canisters. `CanisterCompass` (on the Canvas, arrows under "Compass Arrows", below Game Over and the fader) then pins an arrow to the screen edge for each unfound canister that is off screen.
- `ExitCar` tracks `PlayerInRange` through its `ExitCarZone` trigger child, which must stay on the Default layer, never Wall (wall linecasts hit triggers). The prompt and HUD labels update on events, not per frame.
- Interact (E) at the car with full fuel plays the cutscene: the player gets in (input off, `Rigidbody2D.simulated` off, `PlayerHealth.Invulnerable`, sprites hidden, lights kept as headlights), `ExitCar.DriveOff`, `ScreenFader` to a "LEVEL N" card, `builder.Generate(Rng.Derive(RunSeed, Level - 1), revivePlayer: false)`, then `ExitCar.Arrive` and the player steps out at `PlayerSpawn`. `CameraController.Follow(car)` overrides the camera meanwhile. The first block of the scene also opens with the arrival.
- N and a typed seed (`BlockDebugOverlay`) call `StartRun`/`StartRandomRun`: an instant restart at level 1 with full health, ignored while `Busy`.
- `GameOverScreen` (on the Canvas) shows a moment after `OnDied`, disables gameplay input, and offers Retry (reloads `Block`: a fresh run, same loadout) or Main Menu.

**Player / camera**: The player is found by tag `GameTags.Player` (zombies, `AmmoUI`).
- `CameraController` follows the player. It is pulled toward the cursor by the cursor's offset from the screen center. Measure the offset relative to the camera, never from the cursor's world position, which feeds back on the camera's own position and caused aim shaking.
- `PlayerMovement` moves and aims through the `Rigidbody2D`, using `linearVelocity` and `MoveRotation` in `FixedUpdate` with interpolation. Never move the player with `transform` directly.
  - The aim angle is computed from the interpolated `transform.position`, not `rb.position`.
  - It keeps the last angle while the cursor is within `minAimDistance` (0.5), because a near-zero aim vector jitters.
- `PlayerHealth` initializes in `Awake` and clamps health at 0. It raises `OnHealthChanged` and `OnDied`, and exposes `IsDead`.
- On `OnDied`, `PlayerMovement` and `WeaponManager` disable themselves, and zombies stop: `ZombieAttack.TargetAlive` checks `IsDead`. `GameOverScreen` then takes over (see Level loop).
- `PlayerHealth.Revive()` restores full health and raises `OnRevived`, which turns movement and weapons back on. Both subscribe in `Awake`, not `OnEnable`, because death disables them. Restarts (N, a typed seed) revive the player; the next level of a run does not.
- **Lights:** the Player has two child `Light2D`s, each with a `VisibilityLight`.
  - `Ambient Light`: 360°, radius 2.57.
  - `Flashlight Cone`: 70° outer and 45° inner angle, radius 8, local rotation −90° because 2D lights point along local up and the player aims along +X.
  - `VisibilityLight` reads its reveal area from its own `Light2D` (outer radius and outer angle) and registers in `VisibilityLight.All`. Changing a light's size or angle in the Inspector changes what it reveals.
  - No trigger colliders or `Flashlight` tag are involved.
  - Both lights use shadow intensity 1, so walls stop light completely. Below 1, part of the light shows through walls.

**UI (`Scripts/UI`)**: This is uGUI: `Slider`s, and TMP in the selection screen. There is no legacy `Text`. `HealthBar` updates only on `PlayerHealth.OnHealthChanged`.

**Input:** Input uses the new Input System only. Active Input Handling is "Input System Package", so the legacy `UnityEngine.Input` class throws.
- `Assets/Input/FlickerControls.inputactions` is also the project-wide actions asset. Its `Gameplay` map has Move, Aim, Fire, Reload, SwitchWeapon, Slot1, Slot2, Unequip, Regenerate (N, debug: restart the run on a random block) and Interact (E: drive off in the exit car), with a `Keyboard&Mouse` scheme. It generates the C# wrapper `FlickerControls.cs`; never edit that file.
- `PlayerInputReader` (on the Player, `DefaultExecutionOrder(-100)`) is the only gameplay script that touches input. It exposes `Move`, `AimScreenPosition` and `FireHeld`, plus events (`ReloadPressed`, `SwitchWeapon(int)`, `Slot1Pressed`/`Slot2Pressed`, `UnequipPressed`, `RegeneratePressed`, `InteractPressed`). `BlockDebugOverlay` shows the seed, regenerates on N, and takes a typed seed (a number or any word). It disables the reader while its seed field has focus. `PlayerMovement`, `WeaponManager` and `CameraController` read from it.
- To add a control or a gamepad, edit the asset, then expose the new control on the reader.
- UI uses the EventSystem's `InputSystemUIInputModule` with the package's default UI actions.

**Layers in use:** Wall, Floor, Player, Bullet, Zombie, Obstacle (plus sorting layers Floor, Wall and Player).
- **Wall** blocks movement, light (`ZombieVisibility` linecasts, `ShadowCaster2D`) and bullets. Walls, fences, buildings, the street barrier, cars and trees are on it.
- **Obstacle** (layer 13) only blocks movement and the NavMesh: benches and trash cans. You can see and shoot over it. It is in no `wallLayer` mask, has no shadow caster, and Bullet × Obstacle collisions are off in the 2D physics matrix.
- Level prefabs (`Prefabs/Level/`) are `Square` sprites with an unlit material, a `BoxCollider2D` and a NavMeshPlus `NavMeshModifier` (area Not Walkable).
  - The builder scales the wall/fence/building/barrier blocks. They are variants of `Wall Block`, whose `ShadowCaster2D` must keep **Trim Edge 0**. The trim is in local space, so the scale multiplies it: 0.05 on a 10-long wall left a 0.5 gap at each end, and light leaked through the seams between blocks.
  - Props occupy their `PropKinds.Size` footprint in the layout, and the builder only rotates them. The visible body may be smaller than the footprint (car 1.6×3.4 in a 2×4 stall, trash can 0.6×0.6).
  - The tree casts its shadow from its 0.75 collider (shape-provider source, no self-shadow).
  - Tall things (blocks, cars, trees) use sorting layer **Wall**. Low obstacles (benches, trash cans) use **Floor**, so bullets, zombies and the player draw over them. Sorting layer order: Default (ground tilemap) < Floor < Player < Wall.

## Version control

Remote `origin` is the public GitHub repo `ArtemBereznii/Flicker`. Work goes on `master`, which tracks `origin/master`. The history was restarted from a single clean commit, so there is no older history to dig through.

- `.gitignore` is the standard Unity template plus `.idea/` and `/docs/`. It excludes `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/`, `.vs/`, `*.csproj` and `*.sln`. None of these should ever appear in `git status`. If one does, something was force-added. Never use `git add -f`.
- `.gitattributes` normalizes line endings and marks images, audio and fonts as binary. It routes `*.unity`, `*.prefab`, `*.asset`, `*.anim`, `*.controller` and `*.mat` through the `unityyamlmerge` driver (Unity's `UnityYAMLMerge.exe` from the Editor's `Data/Tools`). No Git LFS is used. Assets are small.
- Assets are serialized as text and `.meta` files are visible. Always commit `.meta` files together with their assets.
- The user handles commits and pushes. Don't commit unless asked.
- Commit messages follow Conventional Commits with a capitalized area scope: `type(Scope): summary`, for example `fix(Enemy): ...`, `feat(Weapons): ...`, `refactor(Player): ...`, `docs(Claude): ...`. Types are `feat`, `fix`, `refactor`, `perf`, `docs`, `chore` and `test`. The body is a short bullet list of what changed. A change spanning several areas uses the broadest scope that fits, such as `Gameplay`.
